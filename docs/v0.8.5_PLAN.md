# IronMesh v0.8.5 — Implementation + Test Plan

**Theme:** Make the OpenClaw channel plugin actually shippable — go
from "alpha library that compiles" to "operators can install it,
trust new peers safely, and use it in production."

**Versioning:** v0.8.5 (Python package) + `@wiztheagent/openclaw-ironmesh-channel@0.1.0` (drop `-alpha` once feature-gates close). Incremental on top of v0.8.4. No protocol changes.

**Already on `main` (uncut):** channel plugin alpha.1 + alpha.2 (lifecycle, outbound, messaging, persistence, peer-mapper, directory adapter). 15 channel tests, 51 ts-client tests, 625+1 Python tests — all green.

## Deferred to v0.8.6 (and later)

These are real items but not blockers for shipping:

- **Multi-peer routing** — currently the channel sends to whatever the IronMesh client's handshake peer is. For multi-peer addressing we need either (a) a daemon-attached client mode (architectural — major work) or (b) one connection per target peer (heavier but simpler). Defer.
- **Setup wizard** (`openclaw channel setup ironmesh`) — interactive flow. v0.8.5 ships with manual `openclaw.json` editing.
- **Offline replay** — cache missed messages, drain on reconnect. Needs daemon-side support (the `get_queued_since` RPC from `OPENCLAW_WS_API_GAPS.md` G2). Bigger lift.
- **Streaming partial replies** — for long LLM outputs.
- **Group / room support** — capabilities.groups stays `false`.
- **npm publish of `@wiztheagent/openclaw-ironmesh-channel`** — install-from-source for v0.8.5; publish at v0.8.6 once we've shaken out integration friction with one or two real users.
- **npm publish of `@wiztheagent/ironmesh-client`** — same logic.

## Detail per item

### 1. TOFU pending-trust gate

**Where:** `clients/ts-channel/src/connection.ts` and `src/plugin.ts`.

**Behavior:**

- Inbound MSG arrives → look up peer record in `PeerMapper`
- If `trust === "trusted"`: deliver to subscribers as today
- If `trust === "pending"` (new peer or never approved): record as
  pending, do NOT deliver, emit a `pendingTrust` event with
  `{nodeId, agentName, fingerprint, lastSeenMs, queuedMessageCount}`
- If `trust === "blocked"`: drop silently, increment counter

Pending messages held in a per-account in-memory queue (cap: 100/peer; overflow drops oldest with warning). On `promote(nodeId)`, queue is drained to subscribers in order.

**Tests:**

- pending peer's MSGs don't reach subscribers (assert `received` is empty after sending)
- after `promote(nodeId)`, pending queue drains in order and subsequent MSGs flow normally
- `block(nodeId)` drops new MSGs and returns ok
- queue cap eviction works (101st MSG to a pending peer drops the 1st)
- pendingTrust event fires on first inbound from unknown peer

### 2. `promote()` / `block()` API + agent tools

**TS API:**

```ts
plugin.trust.promote(accountId, nodeId): Promise<{ok, drained: N}>
plugin.trust.block(accountId, nodeId): Promise<{ok}>
plugin.trust.listPending(accountId): Promise<PeerRecord[]>
```

**MCP-side helpers (Python, in `ironmesh_mcp/server.py` — extends the v0.8.4 surface):**

- `ironmesh_list_pending_trust` → `[{node_id, agent_name, fingerprint, queued_messages}]`
- `ironmesh_trust_peer` → flip a peer to trusted; return drained count
- `ironmesh_block_peer` → flip a peer to blocked

This lets an OpenClaw agent inspect + approve via natural language. Tool count goes 18 → 21.

**Tests:**

- TS: 4 unit tests covering each method's happy + error paths
- Python: 4 unit tests in `tests/test_mcp.py` for the new MCP tools

### 3. `defineBundledChannelEntry` integration helper

**Where:** `clients/ts-channel/src/entry.ts` (new).

**What it does:** dynamic-imports the OpenClaw plugin SDK (`peerDependency`), wraps `ironMeshChannelPlugin(...)` in `defineBundledChannelEntry({...})` with sensible defaults, exports as default. Operators just put `import "@wiztheagent/openclaw-ironmesh-channel/entry"` in their OpenClaw plugin loader.

**Tests:** integration smoke that the import resolves cleanly when `openclaw` peer dep is present (skipped when not). Verified manually as part of step 5.

### 4. `openclaw.json` schema declaration

**Where:** `clients/ts-channel/src/config-schema.ts` (new) — exports the `ChannelConfigSchema` describing `channels.ironmesh.<accountId> = {url, passphrase, name}`. The entry helper from step 3 wires this into the `defineBundledChannelEntry` call.

**Tests:** unit test that the schema accepts a known-good config and rejects a known-bad one (missing required field, wrong type). 4 tests.

### 5. Live e2e against gatekeeper

**Harness:** `scripts/openclaw-channel-smoke.sh` — runs on `wiz` (this box), `ssh`s to `gatekeeper`, builds the channel package, symlinks into `~/.openclaw/plugins/`, registers via `openclaw channel set`, restarts gateway, sends a test turn from this box that targets `thegatekeeper` via the channel, asserts the inbound is logged.

**What it proves that unit tests don't:**

- `defineBundledChannelEntry` actually loads under OpenClaw 2026.4.x
- The plugin's `messaging.subscribe` callback wires correctly into OpenClaw's session router
- A real LLM turn delivered through the channel reaches the agent
- Trust gate works end-to-end (first message from unknown peer goes to pending, tool call promotes, later message delivers)

**Pass criteria:** the agent receives a known marker payload and responds with an LLM-generated reply that comes back over the mesh.

## Risks + mitigations

| Risk | Mitigation |
|---|---|
| `defineBundledChannelEntry` import path changes between OpenClaw releases | `peerDependencies: openclaw >=2026.3` + integration smoke test catches API drift |
| TOFU queue overflow loses messages from a chatty pending peer | 100/peer cap + overflow logged + counter exposed; operator can promote sooner |
| Live e2e harness flakes due to network / gatekeeper state | Make it idempotent + restartable; document manual verification path |
| In-memory pending queue loses on gateway restart | Acceptable for v0.8.5 alpha — pending peers stay pending in persisted state, just lose the queued messages they sent. Document. |
| Multi-peer routing absence makes the channel feel limited | Documented limitation in release notes; v0.8.6 commits to addressing it |
